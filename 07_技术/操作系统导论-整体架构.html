全书总纲：一句话记住这本书

操作系统是一个"幻觉制造商"，而且它必须为幻觉付出代价

你只有 8 个 CPU 核、16 GB 内存、一块磁盘。但你同时开着浏览器、音乐、编辑器、几十个后台进程——每一个都以为自己独占着 CPU 和内存，每一个都以为自己有一大片连续内存，每一个都以为文件"保存好了"就永远不会丢。

这些全是假象。操作系统的全部工作，就是在丑陋的物理事实之上，造出一层干净、稳定、可预测的假象，让你可以在上面盖楼。

但假象不是免费的。这本书真正的主题其实是代价：虚拟化 CPU 要付上下文切换的开销，虚拟化内存要付两次访存的代价，并发要付同步的代价，持久性要付写入放大和恢复的代价。理解了"每个假象的代价是什么"，你才算真的读懂了这本书。

全书只有一个关键问题：操作系统如何将资源虚拟化？

作者在正文里专门用灰色文本框把这个问题单独立出来，并特意区分两件事："为什么"要虚拟化不是主要问题（答案显而易见：让系统更易用）；真正的问题是"如何"虚拟化——用哪些机制和策略？如何做到高效？需要哪些硬件支持？

这个提问方式本身就值得学：把"要不要做"和"怎么做"分开，然后集中火力在后者上。

三大支柱：这三件事撑起了整本书
Virtualization

虚拟化

"怎么让 1 个 CPU 变成无数个？
怎么让每个进程都以为自己独占内存？"
全书篇幅最大的一部分（约一半），又分CPU 虚拟化和内存虚拟化两大块。核心手法是时分共享（CPU）与空分共享（内存）。
Concurrency

并发

"同一块内存，两个线程同时改，会怎样？"
一个程序内部同时做多件事。麻烦在于调度时机不可控，于是需要锁、条件变量、信号量，把"不可控"变回"可控"。全书最烧脑的部分。
Persistence

持久性

"断电的那一刻，数据还在吗？"
内存一断电就没了，数据必须落到磁盘。但磁盘慢、会坏、写入还会被崩溃打断——文件系统就是为了在这种设备上做出"永不丢失"的错觉。

"虚拟化（virtualization）、并发（concurrency）和持久性（persistence）。这是我们要学习的 3 个关键概念……这很合适，因为操作系统的难度差不多是物理学的一半。"

为什么"机制与策略分离"这么重要

把两者分开，就能只改策略而不必重新设计机制。这是模块化原则的实例，也是操作系统几十年演进能持续的底层原因：调度策略换了一代又一代，但"时钟中断 + 上下文切换"这套机制几乎没变——因为它被正确隔离在了策略之外。

关键问题与答案链条

问题：只有少量物理 CPU，怎么提供"有无数个 CPU"的假象？

答案：让每个进程只运行一个时间片，然后切换到其他进程。这就是时分共享（time sharing）。潜在开销就是性能损失——CPU 必须共享，每个进程都慢一点。

机制：受限直接执行（LDE）—— 全书最漂亮的设计之一

矛盾在于：要快，就得让程序直接在 CPU 上跑；要控制，就不能让程序为所欲为。

解法就是把两件事分开做："直接执行"——让程序直接在硬件上跑，速度和预期一样快；"受限"——在启动时先设好硬件限制（陷阱表、时钟中断），等于给 CPU 做 "宝宝防护"：锁好危险柜子、盖住电源插座，然后让宝宝自由行动。

三个必须记住的部件：

① 用户模式 / 内核模式：用户模式下代码受限（发 I/O 会引发异常）；内核模式下操作系统可做特权操作。

② 陷阱 / 系统调用：程序执行陷阱指令，同时跳入内核并提升特权级别；完成后由"从陷阱返回"降回用户模式。系统调用看起来像普通函数调用，是因为 C 库把它包成了过程调用，里面藏着陷阱指令。

③ 陷阱表：发起调用的程序不能指定要跳转的地址（否则它就能跳到内核任意位置，比如"跳过权限检查"），所以内核在启动时用特权指令告诉硬件各种事件该运行哪段代码。这是整个保护机制的根基。

控制权怎么拿回来？—— 从"协作"到"强制"

协作方式（早期 Macintosh、旧 Xerox Alto）：操作系统相信进程会合理运行，运行太久就主动通过系统调用（如 yield）放弃 CPU。

致命缺陷：如果某个进程进入无限循环、从不系统调用，操作系统什么都做不了，唯一办法就是重新启动计算机。

非协作方式：时钟中断。时钟设备每隔几毫秒产生一次中断，当前进程停止，操作系统预先配置的中断处理程序运行——操作系统由此强制拿回控制权。这是现代操作系统的基础。

上下文切换要保存/恢复的寄存器分两类：硬件隐式保存的用户寄存器（存在该进程的内核栈上）和操作系统显式保存的内核寄存器（存在该进程的进程结构里）。后一步让系统"从好像刚刚由 A 陷入内核，变成好像刚刚由 B 陷入内核"。

策略：调度算法的演进，就是"发现问题 → 打补丁"的过程

两个指标（务必分清）：

• 周转时间 = 完成时间 − 到达时间（衡量"多快做完"）
• 响应时间 = 首次运行时间 − 到达时间（衡量"多久有反应"）

核心张力：这两者本质矛盾。想周转时间好，就得先跑短任务（对长任务不公平）；想响应时间好，就得频繁切换（周转时间变差）。你不能既拥有蛋糕又吃掉它。

算法规则与优点致命反例
FIFO
先进先出		 按到达顺序跑完。简单。 护航效应：A=100s 排在 B、C=10s 前面，平均周转 110s
SJF
最短任务优先		 先跑最短的。同时到达时可证明最优：同样负载平均周转降到 50s 任务可随时到达时失效（晚到的小任务仍要等）；且需要预知运行时间
STCF
最短完成时间优先		 SJF + 抢占：新任务到达就比剩余时间。同样负载平均周转 50s 响应时间差：第三个任务必须等前两个全跑完
RR
轮转		 一个时间片后换人。响应时间极好：平均响应 1（SJF 是 5） 周转时间最差之一：平均周转 14，甚至比 FIFO 还差
MLFQ
多级反馈队列		 不需要预知任何信息，靠观察历史行为动态调优先级，同时近似 SJF 又照顾交互 早期版本会被"愚弄"：每跑 99% 时间片就主动放弃 CPU 可近乎独占 CPU
彩票 / 步长
比例份额		 用"彩票"表示份额。彩票是概率性的；步长是确定性的，每轮都精确按比例 彩票需要很多轮才收敛；步长需要全局状态，新进程加入会独占 CPU

MLFQ 的五条规则（这是本节最该背下来的东西）

规则 1：如果 A 的优先级 > B 的优先级，运行 A（不运行 B）。

规则 2：如果 A 的优先级 = B 的优先级，轮转运行 A 和 B。

规则 3：工作进入系统时，放在最高优先级（最上层队列）。

规则 4：一旦工作用完了其在某一层中的时间配额（无论中间主动放弃了多少次 CPU），就降低其优先级（移入低一级队列）。

规则 5：经过一段时间 S，就将系统中所有工作重新加入最高优先级队列。

理解要点：规则 3+4 让它近似 SJF（先假定是短任务，不是就慢慢降级）；规则 5 防饥饿并适应行为变化；规则 4 里"无论中间放弃多少次"这个细节，是为了封堵"愚弄调度程序"的攻击——这正是本书"发现问题→打补丁"风格的典型样本。

第一幕 · 虚拟化（下）：让每个进程都以为自己独占内存

关键问题与答案链条

问题：物理内存只有一份，怎么给每个进程一个独立、连续、互不可见的地址空间？

答案：地址转换（address translation）。程序里看到的全是虚拟地址，由硬件（MMU）在每次访存时翻译成物理地址。

为什么值得这么麻烦？三个理由：易用（程序员不用操心变量放哪）、隔离与保护（一个错误的程序不能读写别人的内存）、灵活性（程序可以按任何方式使用自己的地址空间）。

机制的演进：三代的"问题 → 方案"

第一代：基址/界限（base and bound）。一对寄存器记录进程的起始位置和大小。简单，但整个地址空间必须连续放在内存里——栈和堆之间那一大片空洞也得占着物理内存。

第二代：分段（segmentation）。给地址空间里的每个逻辑段（代码、栈、堆）各配一对基址/界限寄存器。只有用到的部分才占物理内存，于是能装下"稀疏地址空间"。代价是外部碎片：段与段之间的空隙难以利用。

第三代：分页（paging）。把空间切成固定大小的页，物理内存切成同样大小的页帧，用页表记录映射。彻底消灭外部碎片，而且不假设堆和栈往哪长——灵活性最高。

一句话总结这个演进：把"变长的东西"换成"定长的东西"，是解决空间管理问题的通用套路。

分页的三个连带问题（这一节最容易考计算题）

问题①：页表太大。32 位地址空间 + 4KB 页 → 20 位 VPN ≈ 100 万个页表项 × 4 字节 = 每个进程 4 MB 页表！100 个进程就要 400 MB 只为存地址转换。

→ 解法：多级页表（像树一样，只为真正用到的部分建表，几乎不浪费）、更大的页、反向页表、把页表本身也交换出去。

问题②：每次访存变两次。要先读页表拿到物理地址，再读数据。这慢得无法接受。

→ 解法：TLB（地址转换缓存）。绝大多数访存都命中 TLB，几乎不花额外时间。可以说没有 TLB，虚拟内存就不可能实用。

问题③：地址空间可以比物理内存大。怎么做到？

→ 解法：交换空间（把不用的页挪到磁盘）+ 存在位 / 页错误处理（访问不在内存的页就触发页错误，操作系统把它取回来）。

一定要记住的一个小算例（考试和面试都爱考）

地址空间 64 字节，页大小 16 字节 → 共 4 页，虚拟地址需要 6 位：前 2 位是 VPN，后 4 位是偏移量。

假设虚拟地址是 21，二进制 010101 → VPN = 01（第 1 页），偏移量 = 0101（第 5 个字节）。查页表得物理帧号 7（二进制 111）→ 物理地址 = 111 0101 = 117。

关键点：偏移量保持不变。因为偏移量只是告诉你"这是页内的第几个字节"，页内位置不因搬家而改变。VPN 换成 PFN、偏移量原样保留——这就是地址转换的全部秘密。

策略：换出哪一页？

核心视角：把内存看成"所有虚拟页的缓存"。那么目标就是让缓存未命中最少，即从磁盘取页的次数最少。衡量指标是 AMAT = (PHit × TM) + (PMiss × TD)（内存访问成本与磁盘访问成本的加权和）。

策略谱系：最优（OPT，理论下界，不可实现）→ FIFO（简单但差）→ 随机（简单且没有最差情况）→ LRU（用历史预测未来，接近最优但难实现）→ 近似 LRU：时钟算法（实用）。

必须知道的反直觉结论——Belady 异常：对某些访问序列，FIFO 在内存更大时，页错误反而更多。因为它完全不考虑"这页还会不会被用到"。一个策略如果不基于正确的信息，增加资源不保证改善结果，甚至可能更糟。

第二幕 · 并发：当"不可控"成为常态

先看那个著名的例子（第 26 章）

两个线程，各自把同一个共享计数器加 1，各循环 1000 万次。预期结果：2000 万。

有时候确实得到 20000000。但多数时候你得到别的数字——而且每次运行都不一样。

为什么？因为 counter = counter + 1 在机器层面不是一步，而是三步：从内存读到寄存器、寄存器加一、写回内存。而调度器可以在任意两条指令之间切换线程。如果切换正好发生在"读完还没写回"的间隙，另一个线程也读到了同样的旧值——一次加法就凭空消失了。

结论（这句话要背下来）：程序逻辑没错，是你对执行顺序的隐含假设错了。并发 Bug 的本质是：程序实际可能出现的执行顺序，比你假设的要多得多。

机制：先造原子操作，再用它构建一切

锁的四个评价标准：① 是否提供互斥（能阻止多个线程进入临界区）？② 是否公平（有没有线程会饿死）？③ 性能（无竞争时开销多少）？④ 多 CPU 多线程竞争时性能如何？

锁的实现演进：控制中断（只适用单处理器，且要求信任用户程序）→ 测试并设置（test-and-set，自旋锁）→ 比较并交换（compare-and-swap）→ 链接的加载与条件式存储（LL/SC）→ 获取并增加（fetch-and-add）。

自旋的问题与解法：自旋锁简单但空耗 CPU。改进路线：让出 CPU（yield） → 用队列 + 休眠替代自旋（park/unpark），避免无谓的自旋和饥饿。

在这之上构建的一切：并发计数器、并发链表、并发队列、并发散列表——都要考虑锁的粒度和正确性。

条件变量：为什么必须用 while 而不是 if

线程经常需要"等某个条件成立"。简单的方案是自旋检查，但极其低效。条件变量提供了一个显式队列：条件不满足时线程把自己加入队列等待，另一线程改变状态后发信号唤醒。

书里的标准写法是：

Pthread_mutex_lock(&m);
  while (done == 0)           // ← 是 while，不是 if！
    Pthread_cond_wait(&c, &m);
Pthread_mutex_unlock(&m);

为什么不能换成 if？因为被唤醒不等于条件一定成立——可能被"虚假唤醒"，也可能在你醒来之前条件又被别人改回去了。醒来之后必须重新检查条件。这是并发编程里最经典的一个坑。

信号量：一个原语表达两种语义

信号量是 Dijkstra 提出的同步原语，sem_wait() 把值减一（若为负则等待），sem_post() 把值加一（并唤醒等待者）。它同时能表达锁和条件同步：

• 值设为 1 → 就是一把锁（二值信号量）
• 值设为 0 → 用作条件变量（等待某事件发生）
• 值设为 N → 控制同时访问某资源的线程数

用它能解决的经典问题：生产者/消费者（有界缓冲区）、读者—写者锁、哲学家就餐。

注意：不理解 P/V（wait/post）的顺序，几乎必然写出死锁。这是初学者最高频的翻车点。

常见并发缺陷：两大类

非死锁缺陷：① 违反原子性（该原子的操作没保护，如 counter++）；② 违反顺序（该先做 A 再做 B，实际反了）。

死锁缺陷——四个必要条件（缺一不可）：

① 互斥：资源同一时间只能被一个人占用；
② 持有并等待：拿着一个，还在等另一个；
③ 不可抢占：别人不能从你手里抢走；
④ 循环等待：A 等 B，B 等 A。

这四条同时成立才死锁——所以预防的思路极其清晰：打掉任意一条即可。最常用的做法是规定所有人按同一顺序申请资源，直接打破循环等待。

基于事件的并发（进阶）：换一条路

既然并发的麻烦几乎全来自锁，能不能根本不用锁？可以：用一个事件循环，不用多线程。程序守着一个队列等待事件，一个一个处理。没有并发，就没有锁，也没有死锁。

代价立刻出现：任何阻塞的系统调用都会把整个事件循环卡住——你不能一边等磁盘 I/O 一边处理其他事件。于是必须引入异步 I/O；接着状态管理变得极其复杂，因为一次逻辑操作被拆成多个事件，中间状态得手动保存。你消灭了锁的问题，换来了状态管理的问题。

第三幕 · 持久性：在一台会坏的机器上保住数据

先把物理事实搞清楚：磁盘为什么慢

磁盘 I/O 时间 = 寻道时间（磁头移动到正确磁道）+ 旋转延迟（等正确的扇区转到磁头下）+ 传输时间（真正读写数据）。

顺序访问和随机访问的性能差上百倍——因为随机访问意味着磁头要来回寻道，而机械寻道是毫秒级的，比传输数据本身慢几个数量级。

这个物理事实支配了整个存储软件的设计：磁盘调度（SSTF、电梯算法）想把随机变成顺序；FFS 讲究"磁盘意识"、把相关数据放在同一个柱面组；日志结构文件系统（LFS）干脆走极端——把整个磁盘当成一条只追加的日志，永远只顺序写。
很多看起来精巧的系统设计，追根究底只是在绕开一个物理限制。

RAID：用一堆廉价磁盘换性能、容量、可靠性

RAID 对上层透明——操作系统和应用程序看到的就是一个大磁盘，不用改一行代码。这种"透明可部署性"是它成功的关键。

• RAID 0（条带化）：把数据分散到多块盘，容量和吞吐都提升，但完全没有冗余，坏一块就全完。
• RAID 1（镜像）：每份数据写两块盘，能容忍一块盘坏，代价是容量利用率只有 50%。
• RAID 4：用一块专门的校验盘存奇偶校验，能容忍一块盘坏，但每次小写入都要读写校验盘，校验盘成为瓶颈。
• RAID 5（旋转奇偶校验）：把校验块轮流分散到所有盘上，解决了 RAID 4 的校验盘瓶颈，能容忍一块盘坏。

文件系统：inode 是理解一切的关键

磁盘上的一块区域被组织成：超级块（文件系统的元信息）+ inode 位图（哪些 inode 被占用）+ 数据位图（哪些数据块被占用）+ inode 表 + 数据块区。

inode 是什么？它是"一个文件的全部元信息"，但不含文件名。里面有：文件大小、所有者、权限、时间戳，以及最重要的——指向数据块的指针。指针分直接指针、间接指针、双重间接指针，用这种多级结构让一个小 inode 能描述一个很大的文件。

那文件名存在哪？存在目录里。目录本质上是"文件名 → inode 号"的映射表。这解释了硬链接：多个文件名指向同一个 inode，删掉一个文件名，数据仍在（只要还有别的名字指向它）。而符号链接是一个独立的小文件，内容就是另一个文件的路径——它指向的是"名字"，不是 inode。

崩溃一致性：本书的智力高潮

问题：系统可能在任何两次写入之间崩溃。磁盘上的状态可能只更新了一半。怎么保证文件系统还能处于合理状态？

先看一个具体例子（第 42 章）：往一个文件追加数据，需要更新三个磁盘结构——① inode（指向新块、大小变大）、② 数据位图（标记新块已分配）、③ 数据块本身。如果崩溃只完成了其中一两个，文件系统就处于"有趣的状态"：比如 inode 指向了一个还没写入的块，读出来就是垃圾数据。

三种解法，思路层次完全不同：

① FSCK（事后救火）：让系统先坏着，重启后派检查程序把整个磁盘扫一遍，把不一致的地方修好。缺点：慢，而且它不知道本来应该是什么样，只能猜。

② 日志 / 预写日志（事前记账）——最漂亮的解法。在真正动手之前，先把"我打算做什么"写到一个日志区；确认日志落盘后，再去做实际修改。崩溃后重放日志，就能恢复到一致状态。它没有让磁盘变快或变可靠，只是改变了记账的顺序。

③ 写时复制 / 软更新（换思路）：永远不覆盖正在使用的数据，只写新位置，最后用一个原子操作切换指针。让"不一致的中间状态"根本不存在。

顺着思路②走到底，就是日志结构文件系统（LFS）：干脆把整个磁盘当成一条只追加的日志，顺序写到底，用检查点区域和 inode 映射来定位数据。

数据完整性：磁盘也会默默出错

除了"整块盘坏掉"，还有一种更隐蔽的故障：潜在扇区错误——盘还能用，但某个扇区的内容悄悄变了。

解法是校验和（checksum）：为每个块计算一个校验值并存起来，读的时候重新计算并比对，不一致就知道数据坏了。还要处理两种更麻烦的错误：错误的写入（写到了错误的块）和丢失的写入（以为写成功了其实没写）。另外要有擦净（scrubbing）——定期主动扫描所有块，尽早发现坏块。

跨越三部分的工程智慧：这些"提示"才是全书精髓

① 抽象不是"简化"，而是"制造一个可控的假象"

进程、地址空间、文件、目录、RPC——每一个都是假象。真实世界是寄存器、物理页、扇区、丢包的网线。理解这一点，你就不只是在学操作系统，你是在学"如何构造可靠系统"这件更普遍的事。

② 最优雅的方案，往往来自换个"记账方式"

日志（预写日志）没有让磁盘更快或更可靠，它只是换了一种记账顺序：先写下"我打算做什么"，再去做。LFS 把这条思路走到极致：把整个磁盘当成一条只追加的日志。问题的解法常常不在"更强的能力"，而在"更聪明的顺序"。

③ 一个策略如果不基于正确的信息，增加资源反而可能更糟

Belady 异常是最好的例子：FIFO 只看"到达顺序"，完全不看"这页还会不会被用到"，所以给它更多内存，它反而可能淘汰掉马上要用的页。在优化任何东西之前，先问：我的决策依据和我的目标真的相关吗？

④ 尽可能简单；只在需要的时候才并发

作者在并发部分的收尾建议非常直接：尽可能简单，避免复杂的线程交互，优先使用已被证实的交互方式（锁、生产者—消费者队列）；只在需要的时候才并发，尽可能不用它——过早地优化是最糟糕的。如果确实需要并行，用 Map-Reduce 这类简单形式，就不必操心锁和条件变量。

⑤ 也许目标不是找到最好的方案，而是避免灾难

调度策略的争论可能永远不会有结论，因为连度量指标本身都是互相矛盾的（周转时间好，响应时间就差）。所以作者引了 Lampson 的这句话作收束——把"追求最优"的执念，换成"避免最坏"的务实。

"也许目标不是找到最好的解决方案，而是为了避免灾难。"

—— Lampson，被引于第11章 关于 CPU 虚拟化的总结对话

"似乎操作系统相当偏执。它希望确保控制机器。虽然它希望程序能够尽可能高效地运行，但操作系统也希望能够对错误或恶意的程序说：'啊！别那么快，我的朋友。'"
