L1 · 基础（3 题）
1记忆层级有哪几层？为什么它必须存在？L1

从快到慢列出，并说出这个层级存在的根本原因。

展开答案
层速度容量
CPU 寄存器最快最小
CPU 缓存（L1/L2/L3）快小
主存（RAM）慢大
磁盘 / 固态最慢最大

为什么必须存在：因为快的存储器做不大，大的存储器做不快——这是物理与成本的双重约束。

书里用的类比很直观：Fiona 的书桌只能放三本书，门外有书架，校园里有图书馆。她当然希望所有书都在桌上，但桌上放不下。

所以层级的目的是：把"经常用的"放在快的层，把"偶尔用的"放在慢的层——而这个"经常/偶尔"的判断，就是下一题的内容。

⚠️ 失败模式以为这是"工程偷懒"的结果。如果能把 RAM 做到和寄存器一样快，早就不需要缓存了。层级不是设计上的妥协，是物理约束下的最优解。
2时间局部性和空间局部性分别是什么？它们各自决定了缓存的什么设计？L1

说出两者的定义，并指出它们对应缓存的两个不同决策。

展开答案
类型含义决定
时间局部性 刚用过的东西，很可能马上再用 淘汰策略（把谁踢出去）
空间局部性 用了某个地址，附近的地址很可能也要用 块大小（一次搬多少）

而这一层设计只有一个依据，书里的原话是：

"systems look to the past as a predictor of what will likely happen in the future."

为什么只能靠过去：书里说得直接——"hardware designers haven't discovered how to build circuits that can predict the future." 而让程序员提前声明访问模式，对通用系统来说负担太大。

⚠️ 失败模式把两种局部性当成一回事。它们是两个不同的问题：一个管"留谁"，一个管"搬多少"。理解这个区分，才能理解为什么缓存要同时有"块大小"和"替换策略"这两个参数。
3一个函数遍历数组求和——它同时利用了两种局部性吗？L1

用那个 sum_array 的例子说明哪些变量利用时间局部性、哪些利用空间局部性。

展开答案

看这段代码：

int sum_array(int *array, int len) {
    int i, sum = 0;
    for (i = 0; i < len; i++) {
        sum += array[i];
    }
    return sum;
}
变量利用什么局部性为什么
i · len · sum · array（基地址）时间局部性循环每次迭代都访问它们 → 只需从内存载入一次
array[i] 的元素空间局部性每个元素只访问一次，但它们是连续的地址

空间局部性那一条的具体机制（书里的原话）："accessing the first array index fills the cache with not only the first integer, but also the next few integers after it, too."

而它给了一个具体数字：假设块大小是 16 字节，系统一次搬 4 个 int。所以访问第一个元素付一次内存的代价，后面三个都从缓存出——即使程序之前从未访问过它们。

⚠️ 失败模式以为"只访问一次就不会有缓存收益"。恰恰相反：即使每个元素只读一次，顺序访问依然能从缓存获益——因为一次搬了一整块。这是最容易忽略的一点，也是下一题那个 5 倍差距的根源。
L2 · 理解（6 题）
4为什么同一个矩阵遍历，只换索引顺序就快约 5 倍？L2

这是全书最重要的一个例子。请解释两个版本在内存访问层面的实际差别。

展开答案
版本 1（快约 5 倍）版本 2
total += mat[i][j];total += mat[j][i];

书里的解释：

版本 1："accesses the matrix's values sequentially in memory… it pays the cost of going to memory only once for every block of values."

版本 2："accesses the matrix's values by repeatedly jumping between rows across nonsequential memory addresses. It never reads from the same cache block in subsequent memory accesses… Thus, it pays the cost of going to memory for every matrix value it reads."

关键在这里：C 的二维数组是行优先（row-major）存储的——mat[i][0]、mat[i][1]、mat[i][2] 在内存里是连续的。

版本 1版本 2
访问顺序沿内存连续前进在行之间反复跳跃
每块搬进来用几次全部用上只用 1 次就丢
去内存的次数N²/每块元素数N²

而最关键的一点是：两个版本的工作量完全一样——都是 N² 次加法、N² 次数组访问。在 algs4 的代价模型下，它们是一样快的。

🔬 可跑验证 · 这个实验值得亲手做一遍
建一个矩阵，总大小远超缓存（比如 4096×4096 的 float，约 64 MB）。用行优先和列优先两种顺序各遍历求和一次，计时。
预期：行优先明显更快（这个规模上常见 3–10 倍）。
建议再做一步：把矩阵缩小到能装进缓存（比如 256×256），重测——差距会大幅缩小甚至消失。这一步能让你亲眼看到"差距来自缓存，不是来自代码结构"。
⚠️ 失败模式以为"编译器会帮我重排循环"。它常常不能——因为重排可能改变语义（如果循环体有副作用），编译器不敢做。而 mat[i][j] 与 mat[j][i] 这种"看起来等价"的改动，在指针与别名存在的情况下编译器往往无法证明它安全。
5直接映射缓存的地址分成哪三段？各决定什么？L2

说出三段的名字与各自的作用，并解释"直接映射"这个名字的含义。

展开答案
段决定什么
标签（tag）这个位置里是不是我要的那块数据
索引（index）放到缓存的哪一组
块内偏移（offset）在块内的哪个字节

"直接映射"的含义：每个内存块只能放到缓存里唯一一个位置——由索引段直接算出，不需要搜索。

它的优点是快（一次比较就知道命中与否）；代价是冲突缺失——如果两个热点数据恰好映射到同一位置，它们会不停地把对方踢出去，即使缓存里有很多空位置。

⚠️ 失败模式以为"缓存大就不会冲突"。直接映射下，冲突与缓存大小无关，只与地址的索引位是否相同有关。这就是为什么会发展出组相联缓存——用一点硬件复杂度换取冲突的减少。
6直接映射、组相联、全相联三者的取舍是什么？L2

说出三者的机制差别，以及这个取舍的本质。

展开答案
设计块能放哪冲突硬件复杂度
直接映射唯一一个位置高最低（一次比较）
组相联（N 路）组内 N 个位置任选中中（并行比较 N 个标签）
全相联任何位置最低最高（要搜整个缓存）

取舍的本质：灵活性换硬件复杂度。越灵活 → 冲突越少 → 命中率越高；但每次访问要比较的标签越多 → 越慢、越贵、越费电。

所以实践中用的是折中：现代 CPU 的 L1 常用 4–8 路组相联，而全相联只用在小到可以接受的缓存上（比如 TLB）。

⚠️ 失败模式以为"路数越多越好"。路数增加会拉长命中判断的时间——而缓存的全部价值就在于"快"。如果判断命中要花 5 个周期，那不如直接去内存。
7写回（write-back）和写直达（write-through）的取舍是什么？L2

说出两种策略的做法、代价，以及各自适合的场景。

展开答案
策略做法代价
写回 只改缓存，标"脏"；被淘汰时才写回内存 内存写次数少；但要维护脏位，且多核下一致性更复杂
写直达 每次写都同时写缓存和内存 内存写次数多；但简单、一致性好

这个取舍与 OSTEP 里"页表项要维护脏位"是同一类问题——都是"用一点元信息换取更少的慢速写"。

写回在多核下会引出新的问题：如果两个核各有一份同一个地址的副本，其中一个改了，另一个的副本就过期了。这正是第 11.6 节"缓存一致性"要解决的问题，也是第 14 章"缓存一致性"的开端。

⚠️ 失败模式以为"写直达更安全所以更好"。它的一致性优势是真的，但代价是内存带宽被大量浪费在重复写上。现代 CPU 默认是写回——一致性由专门的协议（如 MESI）在硬件层面保证。
8为什么硬件用 LRU 淘汰？它和 OSTEP 里的 LRU 是什么关系？L2

说出 LRU 的依据，并说明这一域两本书在这个点上的衔接。

展开答案

依据就是那句话："systems look to the past as a predictor of what will likely happen in the future."——用过去的访问顺序预测未来。

LRU = Least Recently Used（最近最少使用）：淘汰最久没被访问的那一块。

书里用书本类比讲得很清楚：桌子满了，就把"最久没碰过的那本"收回书架。它抓住了时间局部性的两个目标：常用的留在近处；不常用的终究会成为"最久没用"而被移走。

而这个策略在系统里出现了两次——我核对了两本书的原文：

OSTEP（操作系统）Dive into Systems
问题物理内存满了，换出哪一页？缓存满了，淘汰哪一块？
答案LRU 及其近似LRU
在体系里的层策略——软件可换机制——硬件固定
提到 LRU 的次数44 次19 次

这个连接的价值：同一个策略（用过去预测未来）在从寄存器到磁盘的每一层都被使用。而两本书从两端逼近它——一本从软件策略，一本从硬件机制。

而它正好印证了"抽象→机制→策略"那个框架：在缓存层，机制和策略都由硬件定死（软件改不了）；在虚拟内存层，两者都在操作系统手里（可调）。同一件事在不同层级的可调整程度不同。

⚠️ 失败模式以为硬件能实现完美的 LRU。精确 LRU 需要维护访问顺序，代价高——所以实际硬件用的是近似（如时钟算法、伪 LRU）。而 OSTEP 里也讲了同样的道理：精确 LRU 在软件里也难实现，所以操作系统也用近似。
9用 Cachegrind 能量到什么？为什么"可测量"这件事很重要？L2

说出这个工具的位置与作用，以及它和 algs4 那个方法论的关系。

展开答案

Cachegrind（第 11.5 节）给出缓存缺失次数的统计。Massif（第 12.3.3 节）给出内存使用曲线——程序在什么时候用了多少内存。

两个工具合起来，把"内存"从一个模糊概念变成两个可量化的数：

工具量化的东西
cachegrind缓存缺失次数（按 L1/L2/L3 分别统计）
massif峰值内存占用 + 时间曲线

为什么"可测量"很重要——这是本题的核心。回想 algs4 第 1.4 节那句：

"The experiments we design must be reproducible and the hypotheses that we formulate must be falsifiable."

这一层同样遵守这条纪律。你不需要"相信"局部性理论——你可以测。你可以造两个版本的代码，让 cachegrind 告诉你缺失次数差多少。

而这正是这一域最有价值的地方：在别的域你只能说服自己，在这里你能被数据纠正。

🔬 可跑验证 · 用 cachegrind 量出那个 5 倍
对第 4 题的两个矩阵遍历版本各跑一次 valgrind --tool=cachegrind。
你会看到两个版本的数据缺失次数差异巨大——而指令数几乎相同。这个对比比计时更有说服力：它直接指出了差异的来源，而不只是差异的大小。
⚠️ 失败模式把 cachegrind 的数字当成"绝对真相"。它模拟的是某种缓存配置——反映的是相对差异，不是真机上的绝对次数。用它比较两个版本的优劣是可靠的；用它预测绝对耗时不可靠。
L3 · 应用（4 题）
10"循环交换"是怎么起作用的？什么情况下不能做？L3

说明这个手法的原理、收益，以及它的限制。

展开答案

原理：交换嵌套循环的顺序，让最内层循环访问连续内存。这正是第 4 题那个例子的通用化。

收益：把"每读一个值去一次内存"变成"每读一个块去一次内存"。在最理想的情况下，速度提升等于一个缓存块能装下的元素数（常见 4–16 倍）。

限制（三条）：

  1. 循环体不能有跨迭代的依赖——如果第 i 次迭代依赖于第 i-1 次的结果，交换顺序会改变语义
  2. 别名问题——如果两个指针可能指向同一块内存，编译器无法证明交换安全
  3. 不是所有循环都值得交换——如果内层循环本身已经很长，或者数据能全部装进缓存，收益会消失

而第 12.2 节还讲了两个相关手法：

手法做法目的
循环分裂（fission）把一个循环拆成多个让每次遍历的工作集更小、更集中
循环合并（fusion）把多个循环合成一个减少重复遍历、提高时间局部性

注意这两个是相反的方向——所以"哪个更好"取决于你的数据规模与缓存大小。

⚠️ 失败模式手工做编译器已经会做的优化。第 12 章的基础部分就是讲这个的——先确认编译器没做，再手工做。而且手工重排会让代码更难读，这是有代价的。
11algs4 说"数组和链表遍历都是 O(N)"，这本书会怎么补这句话？L3

说出两者的真实差距、原因，以及在什么情况下这个差距会消失。

展开答案

差距：数组遍历通常明显快于链表遍历（常见 3–10 倍，元素更大时差距更大）。

原因：

数组链表
元素位置连续分散在堆上
访问一个元素时同一块里的后续元素也被载入只载入这一个节点
缓存缺失每块一次每个节点一次

而且链表还有一个额外的代价：每个节点要存一个"下一个"指针——这既占空间（8 字节），又意味着有效载荷占比更低（每个缓存块能装的有效数据更少）。

什么情况下差距消失：

  1. 数据能全部装进缓存——那就没有缺失，数组的空间局部性优势用不上
  2. 访问模式变成随机的——数组的"下一块预取"失去作用
  3. 需要频繁中间插入/删除——那时链表反而赢（数组每次插入要搬移 O(N) 个元素）
🔬 可跑验证 · 量出差距，然后让它消失
① 数组和链表各存 N 个整数，顺序遍历求和，计时；② 改成随机顺序访问，再计时；③ 把 N 缩小到能装进缓存，再计时。
预期：① 数组明显快；② 差距缩小；③ 差距基本消失。
这个三步实验的价值是让你看见：优势来自访问模式，不是来自数组本身。
⚠️ 失败模式得出"数组总是更好"。一旦访问模式变成频繁中间插入/删除，链表的优势就出来了。真实工程里常用的折中是"分块链表"——把两者的优点各拿一半。
12为什么 B 树在磁盘上重要，而在内存里没那么重要？L3

用记忆层级的框架回答，并指出一个现代的转折。

展开答案

用层级框架看很清楚：B 树的节点大小是"一整页"——这正好匹配磁盘以页为单位读写。

红黑树B 树
节点大小1 个键一整页
高度（N=10⁹）约 60约 3
每次节点访问的代价一次内存访问（纳秒）一次磁盘 I/O（毫秒）

在磁盘上：60 次 I/O vs 3 次 I/O = 几秒 vs 几毫秒。这个差距是决定性的。

在内存里：algs4 的命题告诉你红黑树是 2 lg N——而 B 树的高度更小但每个节点内的搜索更贵。在纯内存、纯比较次数的代价模型下，B 树没有明显优势。

但有一个现代的转折：现代 CPU 的缓存层级让"缓存行"也变成了一种"页"——一次缓存缺失要几十到几百个周期。所以 B 树（及其变体 B+ 树、B* 树）在内存数据库里重新获得了优势。这是"硬件改变，结论改变"的又一个例子。

⚠️ 失败模式把"B 树适合磁盘"当成永久结论。正确的说法是"B 树适合访问节点很贵的环境"——而"多贵"取决于硬件。这个表述比前者更耐久。
13多核下为什么"复杂度分析"更不够用了？L3

说出第 14 章揭示的三类新代价。

展开答案

algs4 的全部结论都假设单线程。多核引入三类它不管的代价：

代价机制
同步开销加锁、解锁、等待。而锁的争用会随核数增加而恶化
缓存一致性流量一个核写了共享数据，其他核的副本要失效——这产生大量跨核通信
伪共享（false sharing）两个核改的是不同的变量，但它们落在同一个缓存块里 → 系统仍要来回同步这个块

伪共享是最反直觉的一个：两个线程明明操作的是两个独立变量，逻辑上毫无关系，但因为它们在内存里挨着，性能可能比单线程还差。

这直接解释了为什么"数组比链表快"在多线程下可能反转：数组的密集布局在单线程时是优点，在多线程下可能变成伪共享的来源。

🔬 可跑验证 · 制造一次伪共享
写一个包含两个相邻 int 的结构体数组，让两个线程各更新其中一个字段（互不相干）。
然后把这两个字段用填充隔开（各占一个缓存行），重跑。
预期：有填充的版本明显更快。这就是伪共享——它是"逻辑上无关的变量因为物理上相邻而互相干扰"。
⚠️ 失败模式用单线程的复杂度分析去预测多线程性能。核数越多，偏差越大。而且这不是常数因子的问题——伪共享能让"加了线程反而更慢"。

14这本书的结论在什么条件下会失效？L4

给出三个具体的失效场景。

展开答案
失效场景为什么
① 书里的缓存参数与你机器不同 书用具体块大小（如 16 字节）、具体路数举例。而现代 CPU 有多级缓存、每级参数不同
② 数据规模小于缓存 没有缺失，就没有局部性收益——局部性只在"装不下"时才起作用
③ 优化被别的瓶颈淹没 如果程序 90% 时间在 I/O 或网络等待，把剩下 10% 优化两倍只省 5%

而最要紧的一条是第二条：它意味着很多"应该更快"的优化在小数据上测不出来。

这给了一个很实用的实验纪律：测性能优化时，必须让数据规模超过缓存——否则你测的是噪声。这也是为什么"我本地跑挺快的"经常没有说服力。

⚠️ 失败模式在小数据上做性能优化实验然后得出错误结论。这一层的一切都依赖"数据装不下缓存"这个前提。
15"用过去预测未来"这个策略什么时候会错？L4

说出 LRU 类策略的失效情形，以及这说明了什么。

展开答案

失效情形：

  1. 顺序扫描大数组——每个元素只用一次，"最近使用"与"将来使用"毫无关系。LRU 会不停地把有用数据踢出去装没用的数据。这被称为"缓存污染"。
  2. 循环工作集大于缓存——如果循环遍历的数据比缓存大，每次循环都会全部缺失（而如果用小一点的工作集，命中率会突然变得很好——这是"缓存悬崖"）
  3. 访问模式突变——程序从"反复读 A"切换到"反复读 B"，LRU 需要一段时间才能适应

这说明什么："用过去预测未来"是一个启发式，不是定理。它在访问模式有规律且稳定时有效；在顺序扫描、模式突变、工作集过大时失效。

而这一点与 algs4 里的"随机化算法"形成一个有趣的对照：两者都是"保证不是绝对的"。但随机化保证失效的概率极低（比被闪电击中还低），而 LRU 失效是确定性的——只要访问模式是顺序扫描，它就一定失效。

⚠️ 失败模式以为"硬件设计得很好所以不用担心访问模式"。恰恰相反——你对访问模式的了解，是你能对性能做的最大影响。第 11.3.1 节那个 5 倍的例子就是证明：同样的工作量，只因为访问顺序不同。
16algs4 + 这本书合起来，你对"程序为什么快或慢"的认识完整了吗？L4

说出三块合起来的完整性，以及仍然缺的部分。

展开答案

三块合起来给出的完整图景：

来源回答什么由谁覆盖
算法层 增长级对不对、数据结构选对没有 algs4（代价模型、Proposition）
内存层 访问模式、缓存、局部性 Dive into Systems 第 11–12 章
并发层 同步、一致性、伪共享 Dive into Systems 第 14 章 + OSTEP 并发部分

而这三层的诊断顺序很重要：

① 先看规模 N（太小则一切无意义）→ ② 再看增长级（错了则优化常数无用）→ ③ 再看数据结构（换一个可能省掉一个 log）→ ④ 然后才是访问模式（这一层）→ ⑤ 最后是常数与微优化

仍然缺的部分（诚实列出）：

  • GPU 与分布式性能——Dive into Systems 第 15 章只有三节，是导论
  • 编译器优化的深处——第 12 章讲了"编译器会做什么"，但不深入
  • JIT 与动态语言——本书是 C/汇编视角，对托管运行时（JVM/CPython）覆盖有限
  • 特定领域的性能——数据库、机器学习框架、网络栈各有自己的层级
⚠️ 最后的提醒知道这三层，不等于会优化。真正决定优化成败的是测量——你得知道瓶颈在哪一层。
所以这一域最该养成的习惯是：先测，再改，改完再测。而这两本书给你的所有理论，都是用来"读懂测量结果"的。
